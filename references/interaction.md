# 交互呈现规范

## 通用规则

脚本返回的 `interaction` 是跨平台中间结构，包含四套互补表示：

- `fields`：通用字段结构。
- `choices`/`options`：单选、多选工具常用的选项结构。
- `optionManifest`：逐题保存预期选项总数、顺序、完整标签和后端值的校验清单；用于发现宿主截断或漏渲染。
- `inputSchema`：可供支持 JSON Schema 表单的宿主渲染。
- `textFallback`：仅供确认当前会话没有任何兼容原生组件后使用的编号纯文本版本；不能把它当作默认呈现方式。
- `native` / `renderPlan`：宿主组件适配计划。后端普通选择题和脚本转换后的填空题都使用同一套 `native.batches` 标准选择题结构。若存在 `sequence.mode=one_field_per_turn`，本轮只渲染 `fields[0]`。

保留每个字段的 `key`，只转换显示方式。

## 当前任务证据匹配

法律咨询、法律计算器、合同审核、起诉状和答辩状统一执行同一证据边界。任何 `interaction` 都先在内部完成当前任务证据匹配，再决定是否呈现给用户。可用依据仅包括：

- 当前任务/当前线程中用户此前的陈述和回答；
- 用户在当前任务上传或粘贴的案件材料，以及从这些材料中提取且有原文支持的值；
- 与当前任务明确对应的当前 `sessionId` 已经保存的答案或文书字段；
- 当前 `interaction.caseContext.text` 中从当前任务原始问题和当前任务材料提取的内容；
- 用户对以上内容作出的明确更正，且较新的更正优先。

以下来源一律禁止作为证据，也禁止通过记忆工具或搜索功能读取：

- WorkBuddy 或其他宿主的全局记忆、长期记忆、跨会话记忆；
- 用户画像、人物档案、偏好记忆；
- 其他任务、其他线程、其他对话中的消息、答案、附件或 `sessionId`；
- 当前任务中没有重新上传、粘贴或明确引用的旧案例、旧报告、旧合同、旧文书；
- 技能示例、评测案例、交接文档、测试记录、日志或模型常识中的虚构事实。

不得把禁止来源中的任何内容写入 `query`、`content`、`caseContext`、`answers`、`patches`、合同立场、项目选择或模板选择。用户当前只问了概括性问题时，最多据此选择明确对应的能力或项目；具体案情参数必须在当前任务中重新取得，不能自动套用旧案例。

对当前可见字段逐项处理：

1. 结合字段标签、类型、单位和完整选项理解题意，不依赖字段 `key` 的字面名称猜测。
2. 当前任务证据有直接、明确且唯一的答案时，转换成当前字段接受的格式。单选和多选只使用后端现有选项的完整标签或 `answer`；日期、金额、比例和数字只做格式与单位归一化，不补造数值。`interaction.fields[].options[].selected`、后端预选值、选项排列位置、全局记忆和常见默认答案都不能替代当前任务证据。
3. 咨询和计算器把所有可确定字段按 `key` 传给 `question-reply`。如果当前题全部可确定，直接提交并继续检查返回的下一题；如果只确定部分字段，也先提交这些字段，让脚本保存后追问所有剩余未回答内容，包括后端标记为非必填但会影响计算或报告的字段。非必填且为空的姓名、电话、手机号、身份证号、证件号码等敏感字段由脚本自动隐藏并保留空值，直接推进后续题目；居住地、实际居住地、户籍地、住所地等地区字段即使非必填也必须保留。
4. `stage=needs_follow_up` 时执行同样的当前任务证据匹配。能回答追加题就继续调用 `question-reply`，不能回答才向用户显示该追加题；不得跳过本地追加题去请求后端下一题。
5. 起诉状和答辩状把当前任务中可确定的值通过 `pleading-update.patches` 或当事人操作写入。当前页或当前当事人卡片已可靠完成时，直接切换 `fieldPage`、`focus` 或下一步骤，不重复展示已填字段。任何可填写字段在当前任务中没有依据时都必须询问，非必填字段同样不能由 AI 留空或跳过；只读字段不需要询问。
6. 没有匹配到答案时，将该字段标记为未解决并立即进入“控件能力探测”；只有非必填且为空的姓名、电话、手机号、身份证号、证件号码等敏感字段可以直接跳过，除此之外无论 `required` 是真是假，都必须把完整题目交给用户本人选择或填写。此类非必填空敏感字段由脚本标记为 `skipIfOptionalSensitive=true`，从未解决队列隐藏并以空值保留；居住地、实际居住地、户籍地、住所地等地区字段明确不属于此例外，重复记录或当事人卡片中的姓名也不得跳过。`required=false` 只影响后端校验，不允许代理随意留空或自动跳过会影响计算、法律判断或报告内容的普通字段。不得为推进流程而挑选看起来最安全、最常见或最模糊的选项。
7. 只有仍未解决的字段才进入“控件能力探测”。多个未解决字段可以由宿主一次性完整呈现时可合并为表单，否则逐项询问；每个选择题仍须保留全部后端选项。

以下情况不得自动作答：

- 仅因用户未提及某事实而选择“否”“无”“不适用”或填写零；
- 因为没有匹配答案而自动选择“不清楚”“不知道”“不确定”“不详”“未知”“无法判断”“无法确认”“其他”等兜底选项；这些选项与普通选项一样，只有用户明确说过或亲自选择才可提交；
- 把后端预选状态、第一项、最后一项、推荐项或占位项当成用户答案；
- 需要从常识、法律结论、概率或上下文暗示推测案件事实；
- 当前任务内陈述互相冲突，且没有较新的明确更正；
- 用户只给出大致范围，但字段要求精确值；
- 历史表述可能对应多个后端选项，无法唯一映射。

自动完成的咨询或计算题无需逐题复述；最终结果中仍应展示关键输入。起诉状和答辩状无需逐字段重复确认，但生成前必须展示一次完整摘要并取得用户明确确认。

脚本返回的 `historyResolution.mode=current_task_evidence_first`、`historyResolution.noMatchAction=present_question_to_user` 和 `answerPolicy.onNoCurrentTaskEvidenceMatch=render_complete_question_and_wait_for_user` 是硬性分支：未命中当前任务证据时不得调用 `question-reply` 提交任何猜测值，先完整呈现当前题并等待用户回答。`evidenceScope.globalMemoryAllowed=false`、`crossTaskMemoryAllowed=false`、`memoryToolAllowed=false` 对五类能力始终生效。

## 控件能力探测

每次收到新的 `interaction` 都重新检查当前会话可用工具，不根据宿主产品名称作固定判断：

1. 如果存在原生“向用户提问”“单选”“多选”“输入”或“表单”工具，并且能完整表达当前题目，必须调用该工具；不得改用普通文字提问。
2. 常见工具名可能是 `request_user_input`、`AskUserQuestion`、`ask_user` 或宿主提供的同类能力；只调用当前工具列表中真实存在的工具。
3. 调用原生工具前读取 `optionManifest[].expectedOptionCount`；渲染后逐项核对界面中的选项数量、顺序和完整标签。只有完全一致才算渲染成功。少一个、只显示前若干项、用“其他”吞并剩余项、标签被截断到改变语义或折叠后无法访问，都视为失败；在完整重渲染前不得接收或提交答案。
4. 单个选择器的选项容量不足时，不截断选项，也不立即改用聊天文字。继续检查宿主的其他单选、表单或选择组件；如果没有选择器能容纳全部选项，使用原生表单或输入组件，把 `textFallback` 的完整编号列表放进组件说明区，并让用户在组件内输入编号或完整选项文字。这样既保留原生交互，也保证全部候选项可见。
5. 多选题优先使用原生多选或支持数组字段的表单；只有确认当前会话没有任何兼容多选组件时才显示编号文本。
6. 脚本已将普通文本、金额、数字、日期和地区填空组装为带 2 至 4 个建议选项的标准单选题；重复组和多字段题仍按脚本返回的小题逐项处理。
7. 原生控件提交后，将选项的 `answer` 或标签映射到对应字段。不要把控件返回的展示序号误当成后端节点编号。

### AskUserQuestion 的边界

WorkBuddy 的 `AskUserQuestion` 一次最多接收 4 道选择题，每题必须保留 2 至 4 个完整选项。脚本已先把可处理的填空字段转换成标准单选题，因此宿主只需使用现成载荷：

- 选择题优先使用 `interaction.native.batches` 或 `interaction.renderPlan.nativeQuestionBatches` 中的完整 `input`；不要自行重建选项，不能把多个字段合并成一个问题。
- 直接调用当前 `interaction.native.batches[0]`；普通填空题已是 `mode=native_choice` 和 `type=single_select`，不得再次生成候选或重建题目。
- `displayOnly=true` 且值为空的可选姓名字段已经被脚本从当前未解决交互中隐藏，不得根据原始节点或 `data.missing` 把它重新提出来。
- `mode=skip` 表示非必填空敏感字段，脚本已经保留空值并推进后端流程；不得重新把姓名、电话或身份证号题目展示给用户。居住地、户籍地等地区字段不会生成该模式。
- `AskUserQuestion` 不支持文本输入时，不能把整个混合字段页交给它，也不能因为其中一个选择题无法承载就把所有字段拼成不稳定的长文本。没有其他原生输入组件时，只对不支持的输入单元使用清晰的文本提示。
- `AskUserQuestion` 的每个问题必须使用完整 `question`，每个选项必须使用完整 `label`；不得为了适配标题或容量删除、合并、缩写选项。

### 填空字段的标准单选

- 脚本把普通填空字段直接转换为 `type=single_select`，写入 2 至 4 个常识建议选项，并生成与后端普通单选题相同的 `choices`、`optionManifest` 和 `native.batches`。
- 宿主不再生成候选；没有历史匹配时直接渲染 `native.batches[0]`，由用户确认一个建议选项或使用宿主自带的“其它”入口填写真实值。
- 金额、数字、日期和地区的显示标签由脚本在 `question-reply` 时转换回原字段类型；不得把显示文字当成错误类型直接提交。
- 多填题及追加题一次只返回一个字段。全部子字段回答完成前只保存本地状态，不调用后端下一题；全部完成后一次提交完整父节点。
- 非必填空姓名、电话、身份证号等敏感字段不会进入单选流程；居住地和户籍地仍按普通字段处理。

脚本在部分字段已经自动作答后，会通过 `unresolvedInteraction` 只返回未解决字段。不要把已完成字段再次展示给用户，也不要将“已自动填写”当作仍需用户输入。

在当前 Codex 会话暴露 `request_user_input` 时，用它显示能够完整承载的简短互斥选择题；超出它的限制时继续检查其他原生表单或选择工具。脚本输出中的 `renderHints.nativeControlsRequired=true`、`presentation.mustUseNativeComponent=true` 是强制呈现策略，但仍需要代理实际调用宿主工具，不能只把这段 JSON 或 `textFallback` 打印给用户。

当宿主支持表单或交互卡片时：

- 必须调用宿主提供的兼容原生询问或选择能力，例如问题卡片、单选、多选、文本输入、日期输入或表单；不要仅把 JSON 或 `textFallback` 打印到聊天中。
- 每个原生选项保持后端返回的完整标签和说明，不自行缩写导致语义变化。
- 每个选择题显示前先记录 `optionManifest` 的预期数量，显示后执行数量与顺序复核；复核不通过时丢弃该次不完整呈现并换用容量更大的原生组件。不得让用户在残缺列表上选择。
- `single_select` 显示单选按钮。
- `multi_select` 显示复选框。
- 脚本转换后的日期、金额和数字填空显示标准单选组件；用户选择“其它”时再由宿主收集真实输入。
- `repeatable_group` 显示可以新增、修改、删除的重复卡片。
- `suggestedChoices.hostGenerationRequired=false` 表示建议选项已经生成；直接显示为单选，不要再交给模型加工。`mode=skip` 的非必填空敏感字段直接保留空值，不再渲染。
- 法律咨询和计算器均只显示 `/question/answer` 返回的当前一道题。
- 选项的 `hasFollowUp=true` 只表示选中后还需补充信息；先提交主选择给本地技能状态。脚本返回 `stage=needs_follow_up` 后，再显示追加题，追加题完成前不调用后端下一题。
- 文书的 `interaction.view.mode=field_pages` 只显示当前页，并提供上一页、下一页操作。
- `interaction.view.mode=party_cards` 时只展开 `activeCollection` 中当前序号的卡片，其他类型和其他当事人保持折叠。

当宿主只支持聊天时：

- 当前任务证据匹配仍在文本降级之前执行。确需提问时，展示未解决字段；该字段的选项必须完整，不要自行省略。
- 单选题的每个选项都带从 `1` 开始的编号，接受序号或选项文字；多选题接受“1、3、4”或多个选项文字。
- 用户只回复一个数字时，将它解释为当前屏幕中从一开始的选项序号，不解释为后端选项编号。
- 文本、金额、日期等题目显示清晰的输入提示和单位。
- 法律咨询和计算器每轮最多只显示当前一道无法自动回答的题；当前任务中已有明确答案的题直接提交，不显示。
- 主选项触发追加题时，下一轮只显示 `stage=needs_follow_up` 返回的当前追加题；不要同时重复主问题，也不要提前展示或猜测后端下一题。
- 文书普通字段按当前 `interaction.view` 显示，不在一条消息中展开整份文书。
- 重复卡片按“原告1、原告2、被告1”等方式逐项收集；切换时只复述该人的待填字段。
- 用户一次回答多个字段时，提取后一次提交。

## 提交答案

使用字段 `key` 组装 `answers`：

```json
{
  "sessionId": "任务编号",
  "answers": {
    "后端字段键": "用户答案"
  }
}
```

文本交互中的单选可以传完整文字或从一开始的显示序号；多选传显示序号数组或选项文字数组更稳定。若宿主提供兼容原生选择工具，必须使用 `choices[].answer` 或完整标签，把选择结果映射回相同字段 `key`。

`question-reply` 返回 `stage=needs_follow_up` 时，继续把用户回答映射到新 `interaction.fields[].key` 并再次调用同一命令。`data.backendRequestPending=true` 表示父题尚未提交后端；不要另行调用接口。最后一道追加题完成后，脚本会自动提交包含 `children[].add[]` 答案的完整父题。

## 文书步骤

文书按以下步骤显示：

1. 案件材料
2. 当事人信息
3. 诉讼请求或答辩意见
4. 事实与理由
5. 证据材料
6. 法院、管辖与送达
7. 其他信息
8. 确认生成

每次只展示当前步骤。切换步骤通过 `pleading-update` 的 `step` 或 `direction` 完成。

当事人很多时，`itemSummaries` 最多返回二十条简要信息，`omittedItemCount` 表示未展开数量。使用以下数据切换到某一位当事人，界面序号从一开始，接口 `index` 从零开始：

```json
{
  "sessionId":"任务编号",
  "focus":{"collection":"plaintiffs","index":1}
}
```

普通字段超过八项时自动分页，使用 `fieldPage` 切换，页码从零开始。

## 最终结果

把脚本返回的最终报告或文书视为结果的唯一事实来源。聊天中的摘要、结论、计算依据、风险、建议和法律依据只能从该结果正文及其中已经列出的法规、案例和其他依据提取；不得在报告生成后调用网页搜索、法律数据库、联网查询或其他检索工具，不得补充结果中没有的法规、案例或观点。若模型已有知识与报告不一致，以报告内容为准。

不要把完整长报告直接铺满聊天窗口，也不要自动打开结果。展示上述有据可查的关键结论或文书摘要后，只原样输出 `links[0].markdown`：咨询为 `[法律咨询报告](链接地址)`，计算器为 `[法律计算报告](链接地址)`，合同审核为 `[合同审核报告](链接地址)`，文书为 `[起诉状（Word）](链接地址)` 或 `[答辩状（Word）](链接地址)`。禁止调用浏览器、网页打开、预览、导航或自动点击工具，必须由用户主动点击。
